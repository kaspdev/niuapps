## Правило ведения статуса

Этот файл — единая контрольная точка проекта. После каждой существенной работы агент обязан:
1. Обновить этот файл в GitHub: отметить выполненное только после фактического изменения и проверки.
2. Обновить Issue #1, если изменились задачи или их статусы.
3. В ответе в чате показывать тот же краткий статус: что сделано сейчас, что не сделано, что заблокировано и чем проверено.
4. Для каждого пункта указывать доказательство: commit/PR, файл/путь, тест, CI run или APK artifact.
5. Не переводить пункт в «выполнено» по одному лишь наличию документации, плану или заявлению. Нужны исходники и проверка.
6. Если код изменён, но проверка не выполнена, ставить «Реализовано, не проверено», а не «Выполнено».
7. Не терять историю: добавлять новую запись в журнал обновлений ниже, не стирать прежние результаты.

## Значения статусов

- **Выполнено и проверено** — код/настройка реально изменены, соответствующая проверка прошла; приложено доказательство.
- **Реализовано, не проверено** — изменение внесено, но нет успешного теста/сборки/runtime-проверки.
- **Частично** — реализована только часть требования.
- **Не выполнено** — реализация отсутствует или не обнаружена.
- **Заблокировано** — дальнейшая работа невозможна без исходников, доступа, ключей, устройства или данных.
- **Документировано, код не проверен** — есть описание, но исходники/тесты не подтверждают поведение.

## Блокеры

1. Извлечь и проверить содержимое ZIP 1.3.2 либо получить свежий полный исходный проект.
2. Получить stacktrace экрана Admin/Keys, если он не воспроизводится по исходникам.
3. Для проверки BLE/network pairing потребуется Android-устройство.
4. Для подписанных Release APK нужны пользовательские signing secrets; значения секретов не публиковать.
5. Для удаления ветки и смены visibility использовать GitHub UI с правами владельца; перед сменой visibility проверить доступ и интеграции.
